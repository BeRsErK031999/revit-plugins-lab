## 1. Что это за плагин

«Ведомость отделки» — модуль набора плагинов **TrueBIM для Autodesk Revit**. В интерфейсе он находится на вкладке **TrueBIM**, в панели **АР**, под кнопкой **«Ведомость отделки»**. Это не самостоятельное приложение и не Dynamo-граф: штатный пользовательский запуск реализован командой Revit `IExternalCommand`.

Инструмент автоматизирует подготовку ведомости отделки помещений по уже смоделированным физическим элементам. Он:

- выбирает валидные помещения нужной области;
- находит отделочные стены, полы и потолки по классификации типов;
- вычисляет геометрические контакты элементов с помещениями;
- определяет единственное помещение-владельца каждого учтённого элемента;
- получает полную системную площадь этого элемента из Revit;
- читает текст состава отделки из выбранного параметра типа;
- объединяет одинаковые описания и суммирует площади;
- группирует помещения с одинаковым составом отделки;
- записывает подготовленные текстовые значения в параметры помещений;
- при включённой опции записывает принадлежность в сами элементы отделки;
- создаёт новую обычную спецификацию категории «Помещения» с зафиксированными значениями выпуска;
- сохраняет предыдущие выпуски и возможность выбирать связанные помещения через строки спецификации.

Плагин **не моделирует отделку**. Он не создаёт стены, перекрытия или потолки на основе названия помещения. Он не выводит состав автоматически из материалов слоёв конструкции: источник описания — выбранный текстовый параметр типа. Стоимость, нормы расхода, коэффициенты запаса, закупки и сметные расценки в рассматриваемом модуле не рассчитываются.

## 2. Главные правила текущей реализации

Эти положения важнее устаревших комментариев и раннего `ROADMAP.md`:

1. **Контакт определяет владельца; итоговое количество берётся из полной площади элемента.** Площадь пересечения используется для сравнения претендующих помещений, а не как опубликованная площадь отделки.
2. **Один физический элемент учитывается один раз.** Общий потолок над несколькими помещениями не разбивается автоматически на части ведомости.
3. **Владельцы определяются среди всех валидных помещений активного документа.** Выбранный этаж или секция ограничивают выдаваемый результат после определения владельцев.
4. **Помещения группируются по нормализованным описаниям включённых категорий и состоянию расчёта.** Площади, номера помещений, ID типов и количество физических элементов в ключ группы не входят.
5. **Во все помещения группы записываются одинаковые групповые суммы.** Эти выходные площади нельзя затем бездумно суммировать по отдельным помещениям: получится повторный учёт.
6. **Каждое формирование создаёт отдельный выпуск.** Даже когда изменений обычных выходных параметров нет, новый вид и параметры выпуска всё равно создаются.
7. **Выпуск остаётся спецификацией настоящих помещений.** Данные находятся в `SectionType.Body`, а не заменяются статическими строками заголовка.
8. **Числа внутри алгоритма остаются числовыми до финального форматирования.** В выходных параметрах помещений площади хранятся текстом с двумя знаками после запятой.
9. **Предпросмотр не меняет модель.** Запись начинается после отдельного подтверждения в интерфейсе плагина.
10. **Последние изменения источника состава и оформления имеют отдельный статус проверки.** Их наличие в исходниках не означает, что они уже проверены в реальном Revit.

## 3. Какие объекты Revit участвуют

| Сущность | Физическая категория Revit | Роль |
| --- | --- | --- |
| Помещение | `OST_Rooms`, класс `Architecture.Room` | Объект назначения отделки и строк спецификации |
| Отделочная стена | `OST_Walls` | Стеновая отделка, в том числе отдельные участки и откосы, смоделированные стенами |
| Пол | `OST_Floors` | Перекрытие, классифицированное как отделка пола |
| Потолок через перекрытие | `OST_Floors` | Перекрытие, классифицированное как потолочная отделка |
| Штатный потолок | `OST_Ceilings` | Потолочная отделка соответствующего типа |

Работа ведётся с **активным `Document`**. Обход `RevitLinkInstance` и расчёт отделки из связанных RVT-моделей в текущем модуле не реализованы. Границы помещения, существующие благодаря связи, сами по себе не превращают связанные отделочные элементы в поддерживаемый источник.

Не подключены произвольные семейства отделки, обобщённые модели, детали, покраска граней, материалы всех слоёв, плинтусы с измерением длины и специальные категории, которых нет в перечисленном сборщике. Если откос смоделирован стеной подходящего типа, он может участвовать в стеновом расчёте; если он смоделирован другой категорией, одного геометрического сходства недостаточно.

### 3.1. Условия пригодности помещения

`RoomScopeService` принимает помещение, если:

- есть `Location`;
- `Area` — конечное положительное значение больше `1e-9` во внутренних единицах Revit;
- доступен bounding box.

Отдельно во время геометрического расчёта требуется получить непустой `Solid` помещения. Проверяются наличие граней и объём больше `1e-12` во внутренних единицах.

Неразмещённые помещения, помещения с нулевой/некорректной площадью и без bounding box исключаются. Проверка «замкнутости» в чистом сервисе основана прежде всего на площади; это не самостоятельный анализ топологии контура.

### 3.2. Фазы и варианты проекта

В текущем `FinishScheduleSettings` **нет выбора фазы или варианта проекта**, а сборщик помещений не задаёт явный фильтр выбранной фазы. Поэтому фразу старого ТЗ «все помещения выбранной фазы» нельзя выдавать за реализованную пользовательскую настройку.

Фаза и доступность помещений для обычной спецификации остаются существенными свойствами Revit. Несовпадение точного набора помещений нового выпуска с расчётным набором приводит к ошибке проверки и откату. Для моделей с несколькими фазами, вариантами и перекрывающимися помещениями разных стадий нужен отдельный анализ; универсальная корректность таких сценариев имеющимися отчётами не доказана.

## 4. Классификация отделки

Классифицирующий параметр фиксирован: **«Группа модели»**, читается у **типа**, а не у экземпляра. Для классификации сборщик получает параметр по этому имени. В отличие от настраиваемых ссылок на параметры, здесь имя является частью контракта реализации.

| Логический вид отделки | Значение по умолчанию | Допустимый физический источник |
| --- | --- | --- |
| Стены | `Внутренняя отделка` | Стены |
| Полы | `Пол` | Перекрытия |
| Потолки | `Потолки` | Перекрытия и штатные потолки |

Значения настраиваются пользователем. Сравнение выполняется после `Trim()`, без учёта регистра (`OrdinalIgnoreCase`). Это точное сопоставление целого значения, а не поиск подстроки и не распознавание назначения элемента по имени.

Элемент исключается из классифицированных кандидатов, если тип не найден, параметр отсутствует, значение пустое или не совпадает с настройкой. Отсутствующие и неоднозначные классификации учитываются в диагностике; обычное несовпадение значения означает, что элемент не выбран как отделка.

Если для включённых полов и потолков задать одинаковое значение, перекрытие может одновременно подойти обеим категориям. Классификатор считает это `AmbiguousFloorClassification` и пропускает элемент. Поэтому значения полов и потолков должны различаться.

## 5. Откуда берётся описание состава

На весь расчёт выбирается **один текстовый параметр типа**. Он используется для всех включённых видов отделки. Раздельные источники описания для стен, полов и потолков в модели настроек не предусмотрены.

В текущих изменениях 0.2.21 действует такой порядок автоматического подбора:

1. Сохранить явно выбранный совместимый источник, если он не является системным «Имя типа».
2. Для устаревшего выбора «Имя типа» искать совместимый **«• Состав»**.
3. Если такого подходящего параметра нет, искать **«Состав»**.
4. Если источник не найден или неоднозначен, оставить необходимость выбора в «Конфигурации проекта».

Системный `SYMBOL_NAME_PARAM` / `ALL_MODEL_TYPE_NAME`, ID `-1002001`, исключён из списка источников и дополнительно отклоняется валидатором формирования. Это правило распознаёт именно системную identity параметра, а не любые произвольные текстовые параметры с похожим названием.

Выбор параметра `• Состав` вместо `Имя типа` изменяет тексты и может изменять количество групп, поскольку несколько типов могут иметь одинаковый состав. Сам по себе такой выбор не меняет правило получения полной площади физического элемента.

Пустое значение состава не подменяется именем типа. Оно выводится как **`[Описание не задано]`** и сопровождается предупреждением. Внутри построения снимка этот же маркер может появиться, если описание конкретного элемента/типа не удалось разрешить. Не следует обещать, что любой отсутствующий параметр на отдельном типе обязательно будет обнаружен как блокировка ещё до расчёта: каталог проверяет совместимость по собранным данным категорий, а снимок имеет собственный fallback.

Текст состава читается как готовое описание. Плагин не интерпретирует перечисленные в нём толщины, слои и материалы как отдельные измеряемые позиции. Например, строка «Штукатурка 20 мм; грунтовка; окраска» остаётся одним описанием с одной площадью.

### 6.1. Что делает «Добавить параметры по умолчанию»

После подтверждения пользователя сервис:

- создаёт недостающие общие текстовые параметры с постоянными GUID;
- добавляет нужные привязки к категориям;
- расширяет совместимую существующую привязку, сохраняя уже привязанные категории;
- оставляет существующие совместимые определения и их значения;
- при несовместимом одноимённом параметре сообщает предупреждение вместо принудительной замены типа данных или привязки;
- обновляет каталог и повторно подбирает настройки интерфейса.

Существующие привязки ищутся по имени без учёта регистра. Следовательно, уже существующий совместимый проектный или общий параметр может использоваться без замены на стандартный GUID TrueBIM.

Файл общих параметров: `%APPDATA%\TrueBIM\BimTools\finish-schedule\default-shared-parameters.txt`. На время операции меняется `Application.SharedParametersFilename`, после неё прежний путь восстанавливается в `finally`.

**Особенность обработки ошибок:** сервис перехватывает исключения отдельных параметров, собирает предупреждения и может успешно завершить транзакцию с частью обработанного комплекта. Добавление стандартного комплекта не следует описывать как безусловную гарантию «либо созданы все 11, либо не создан ни один». Это отличается от атомарного формирования самой ведомости.

Кнопка не заполняет фактический состав отделки и не назначает элементам правильные значения «Группа модели». Эти данные нужно подготовить в проекте.

## 7. Каталог параметров и защита от неправильного выбора

При открытии команда собирает каталог параметров помещений, стен, перекрытий и потолков. Каталог различает:

- системный параметр: `BuiltInParameterId`;
- общий параметр: GUID;
- проектный параметр: `DefinitionElementId`;
- привязку к типу или экземпляру;
- тип хранения значения;
- категории, на которых параметр найден;
- количество наблюдений и доступность записи.

У `ParameterReference` есть стабильный ключ:

```text
IdentityKind:identity:BindingKind:StorageKind
```

Имя не используется как единственный идентификатор при самой записи. Это помогает не спутать одноимённые параметры разных происхождений. При переносе конфигурации между проектами resolver сначала пытается сопоставить точную identity, затем переносимую identity/однозначное совпадение имени, привязки и типа хранения. Project `ElementId` сам по себе не является глобальным идентификатором между RVT.

Правила совместимости:

| Роль | Привязка | Тип хранения | Дополнительные условия |
| --- | --- | --- | --- |
| Источник описания | Тип | String | Доступен у включённых физических категорий; системное имя типа запрещено |
| Пользовательский идентификатор помещения | Экземпляр | String | Категория «Помещения» |
| Выходы помещений | Экземпляр | String | «Помещения», доступность записи |
| Принадлежность отделки | Экземпляр | String | Соответствующая физическая категория, доступность записи |
| Параметр секции | Экземпляр | String / Integer / Double / ElementId | Категория «Помещения» |

Один выходной параметр нельзя использовать одновременно, например, для описания стены и площади пола. Пользовательский идентификатор помещения и параметр секции также нельзя назначать в выходы: иначе запись испортила бы входные данные.

Каталог строится по реально присутствующим экземплярам и их типам. Отсутствие образцов категории может мешать подобрать источник, даже когда определение параметра формально существует. В частности, UI проверяет потолочный источник по `OST_Ceilings`, тогда как расчёт потолков также принимает `OST_Floors`. Проект, где потолки смоделированы только перекрытиями и нет штатных потолков, требует проверки совместимости каталога; поддержку такого сочетания нельзя выводить только из таблицы категорий геометрического движка.

## 8. Настройки текущего расчёта

| Настройка | Варианты / значение по умолчанию | Влияние |
| --- | --- | --- |
| Стены, полы, потолки | Все три включены | Какие категории искать, группировать, записывать и показывать |
| Классификация каждой категории | См. раздел 4 | Какие типы считаются отделкой |
| Источник описания | Выбранная `ParameterReference`; автоподбор `• Состав`, затем `Состав` | Текст и группировка |
| Идентификатор помещения | Номер / Имя / пользовательский текстовый параметр; по умолчанию Номер | Список помещений и значения принадлежности |
| Записывать принадлежность | По умолчанию выключено | Нужно ли обновлять параметры физических элементов |
| Выходные параметры | Список + описание/площадь каждой включённой категории | Куда записывать итог |
| Область | Этаж / секция или корпус / весь объект; по умолчанию весь объект | Какие помещения попадут в результат |
| Название вида | `Помещения • Ведомость отделки помещений` | Базовое имя нового выпуска |
| Ширина списка помещений | 40 мм | Ширина первого столбца |
| Ширина описаний | 80 мм | Общая ширина всех столбцов описания и расчёт переносов |
| Ширина площадей | 25 мм | Общая ширина всех столбцов площади |

Настраиваемые ширины ограничены диапазоном **10–200 мм**. Столбец «Примечание» имеет отдельную фиксированную ширину **30 мм**.

Отключённая категория не участвует в ключе группы, не требует своих выходных параметров, не добавляется в ведомость и не записывается. Ранее записанные значения отключённой категории при этом специально не очищаются.

Если выбранный идентификатор помещения пуст, используется `#<ElementId>` и создаётся предупреждение. Номера/имена сортируются естественно: числовые фрагменты сравниваются как числа, чтобы, например, 2 шло перед 10. Для надёжной эксплуатации желательно иметь уникальные идентификаторы; отсутствие отдельного запрета повторяющихся пользовательских обозначений не делает их безопасными для всех сценариев группировки и миграции архивов.

## 9. Область отчёта

**По этажу:** выбираются валидные помещения с заданным `LevelId`. Уровень выбирается из каталога проекта.

**По секции или корпусу:** выбирается параметр экземпляра помещения и вводится значение. Плагин сопоставляет его с сохранённым/отображаемым значением параметра. При построении плана фильтра выбранные помещения должны дать одно однозначное исходное значение (`RawValue`). Если одно отображаемое значение соответствует нескольким разным исходным значениям, план спецификации не строится.

**По всему объекту:** все валидные помещения, собранные в активном документе, без дополнительного пользовательского фильтра уровня/секции.

Это не расчёт только выделенных объектов и не расчёт видимого фрагмента активного вида. В настройках такого режима нет.

## 10. Интерфейс и сценарий пользователя

Основное окно — модальное WPF-окно `FinishScheduleWindow` на общей оболочке TrueBIM. Оно содержит настройки текущего запуска: категории, принадлежность, область, имя и размеры ведомости. Подробная настройка классификации, источника, идентификатора и выходов вынесена в **«Конфигурацию проекта»**. Историческое описание «восемь блоков в одном окне» не следует принимать за точную схему текущего интерфейса.

Основные действия:

- **Конфигурация проекта** — настройка соответствия параметров; импорт/экспорт JSON.
- **Добавить параметры по умолчанию** — отдельное изменение параметров проекта после подтверждения.
- **Методичка** — встроенное подробное руководство.
- **Предпросмотр** — расчёт без транзакций записи модели.
- **Предупреждения / сводка** — понятные пользователю замечания, причины и действия.
- **Сформировать** — новый расчёт, подготовка плана записи, подтверждение, запись и выпуск.
- **Копировать отчёт** — полный текст в буфер обмена.
- **Открыть спецификацию** — закрывает окно инструмента и делает созданный вид активным в Revit.
- **Сохранить настройки** — сохраняет локальный профиль, в том числе незавершённую конфигурацию.
- **Закрыть** — сохраняет профиль и закрывает окно.

### 10.1. Первичная подготовка координатором

1. Подготовить размещённые помещения с корректными границами.
2. Проверить физическое моделирование отделки и её категории.
3. Заполнить «Группа модели» у типов.
4. Заполнить общий для включённых категорий текстовый источник состава.
5. Создать или выбрать текстовые выходные параметры помещений.
6. При необходимости настроить параметры принадлежности.
7. Подготовить обязательный шаблон оформления без пустой строки, описанный ниже.
8. Проверить выбранные параметры в «Конфигурации проекта», сохранить профиль или экспортировать конфигурацию.

### 10.2. Обычный запуск

1. Открыть проект и команду TrueBIM → АР → «Ведомость отделки».
2. Убедиться, что выбран правильный документ и источник состава.
3. Включить нужные категории и выбрать область.
4. При необходимости включить запись принадлежности.
5. Задать базовое имя и размеры столбцов.
6. Выполнить предпросмотр и прочитать сводку, особенно пропуски и неоднозначные контакты.
7. Нажать «Сформировать». На этом этапе расчёт выполняется заново и строится конкретный план изменений.
8. Проверить сообщение о заменяемых/очищаемых значениях и новом выпуске. Подтвердить операцию.
9. Прочитать итог и предупреждения; открыть созданную спецификацию.
10. Проверить оформление на листе и сохранить RVT обычными средствами Revit, если результат принят.

Формирование не вызывает автоматическое сохранение RVT или синхронизацию с центральной моделью. Оно изменяет открытый документ; сохранением проекта управляет пользователь.

### 10.3. Предпросмотр и формирование проверяются по-разному

Для предпросмотра достаточно включённой категории, непустой классификации и корректно заданной области. Настройка всех выходов ещё не обязательна. При отсутствии источника описания возможно получить геометрическую сводку без готовой агрегации.

Для формирования нужна полная совместимая конфигурация, валидные целевые помещения, доступность записи, возможность сохранить старые выпуски и корректный шаблон оформления.

Предпросмотр — сводка расчёта и диагностика, а не обещание интерактивной редактируемой таблицы всех результатов. Изменение настроек делает предыдущий результат интерфейса неактуальным. Формирование не применяет автоматически давно сохранённый расчёт без новой подготовки.

```text
FinishScheduleCommand

  → загрузка/сопоставление локальных настроек
  → FinishScheduleWindow

Предпросмотр / Prepare:
  Collect → Scope + Classification + Spatial Index
  → Contacts for ALL valid rooms

Формирование:
  → Room targets + Ownership targets + Schedule plan

```

## 12. Сбор данных и предварительный поиск

`FinishElementCollector` за один этап расчёта собирает помещения, экземпляры стен, перекрытий и потолков, затем уникальные используемые типы. В снимках хранятся ID, тип, категория, уровень, bounds и нужные значения параметров. Координаты bounding box переводятся в мировую систему через его `Transform`.

`FinishClassificationService` отбирает физическую отделку по правилам раздела 4. `FinishBoundingBoxIndex` исключает элементы без bounds из пространственного поиска, сортирует оставшиеся по `MinX` и прекращает просмотр, когда очередной `MinX` уже правее максимума области. Затем проверяется пересечение по всем координатам.

Это простой индекс отсортированных bounding box, а не отдельная GIS-база или сложное пространственное дерево. Его назначение — уменьшить число дорогих геометрических операций.

Кандидат, чей bounding box пересёк область поиска, ещё не считается принадлежащим помещению. Требуется подтверждённый контакт или предусмотренное продолжение стенового контура.

## 13. Границы поиска и этажность

Актуальную область строит `FinishRoomSearchBounds`.

- Горизонтальный допуск: **0,05 фута = 15,24 мм**.
- Для пола начальная вертикальная область — **±304,8 мм** от нижней границы помещения. С 0.2.22 она расширяется до фактических bounds классифицированных полов того же уровня, пересекающихся с помещением в плане с учётом допуска. Пол с известным другим `LevelId` не допускается к этому помещению; подтверждение контакта остаётся геометрическим.
- Для стен и потолков нижняя граница: основание помещения минус горизонтальный допуск.
- Верхняя граница для стен и потолков: основание ближайшего валидного помещения выше, расположенного на другом уровне и перекрывающего текущее по bounding box в плане, минус допуск.
- Если такого помещения выше нет, используется практически неограниченный верхний предел (`double.MaxValue` с поправкой), а не высота текущего помещения плюс фиксированная надбавка.

Промежуточное помещение в другом крыле здания, которое не пересекается в плане, не должно обрезать поиск высокого потолка. Но верхняя граница определяется bounding box помещений, а не точным пересечением их контуров; для сложной планировки это остаётся существенной особенностью.

Дополнительное правило стен: если на базовом уровне стены есть валидные помещения, контакт с помещением другого уровня отбрасывается. Это защищает от переноса стены верхнего этажа вниз из-за отрицательного смещения её основания.

В коде остаётся `FinishCandidateSearchRules.CreateSearchBounds` со старой константой поиска потолка около 2 м. Наличие этого метода не означает, что основной современный расчёт по-прежнему ограничен этим диапазоном: основной путь использует `FinishRoomSearchBounds`.

## 14. Геометрия помещений и элементов

На один расчёт создаётся `FinishRoomGeometryCache` с одним `SpatialElementGeometryCalculator`. Граница запрашивается на отделочной поверхности: `SpatialElementBoundaryLocation.Finish`.

Для комнаты кэшируются `Room`, `SpatialElementGeometryResults` и `Solid`. Для физических элементов `FinishElementGeometryCache` получает solid-геометрию с:

```text
DetailLevel = Fine
ComputeReferences = false
IncludeNonVisibleObjects = false
```

Геометрические экземпляры раскрываются через `GetInstanceGeometry()`. Пустые и практически нулевые тела отбрасываются. Результаты неудачного чтения геометрии элементов также кэшируются, чтобы не повторять одинаковую неудачную операцию.

Эти кэши живут в рамках отдельного расчёта. Это не постоянный межзапусковый кэш и не фоновой наблюдатель за изменениями RVT.

Revit API используется синхронно в контексте команды. В модуле нет переноса Revit-геометрии в `Task.Run`/`Parallel.ForEach`; отдельного пользовательского механизма отмены длительного расчёта по `CancellationToken` также не реализовано.

## 15. Как определяется геометрический контакт

`PhysicalFinishQuantitySource` комбинирует несколько методов. Все они формируют контактные оценки до окончательного назначения владельца.

### 15.1. Прямые граничные подграни помещения

Для каждой грани room solid читаются `SpatialElementBoundarySubface`:

- `Side` рассматривается как стеновая отделка;
- `Bottom` — как пол;
- `Top` — как потолок.

Если `HostElementId` соответствует классифицированному элементу нужной категории, площадь его подграни добавляется в контакт. Несколько подграней одной пары помещение/элемент суммируются. Метод обозначается `RoomBoundarySubface`.

Это надёжный прямой источник связи, но не вся отделка обязательно становится непосредственной границей room solid. Поэтому есть дополнительные способы.

### 15.2. Резервный контакт стены с тонким объёмом у границы

У вертикальных плоских граней помещения создаются тонкие объёмы в обе стороны. Характерная толщина — **0,05 фута**. Они пересекаются с телами стены. На результате выбирается подходящая параллельная грань, чтобы получить оценку площади контакта.

Для одного тела выбирается лучший результат среди probe-граней, затем результаты отдельных тел суммируются. Прямо найденные граничные стены повторно этим методом не добавляются. Метод — `WallProbeIntersection`.

### 15.3. Контакт пола

Для пола используются тонкие горизонтальные probe-объёмы около нижних поверхностей помещения и пересечение с телами перекрытия. Основной метод требует противоположные горизонтальные грани перекрытия; на пересечении выбирается горизонтальная площадь.

Если сложная булева операция не проходит, предусмотрено разбиение probe на более простые треугольные призмы. Это резерв расчёта контакта, а не основание заменить конечную площадь приблизительной.

Метод — `FloorProbeIntersection`. Неподдержанная основным методом форма может получить контакт дополнительным проецированием; само наличие предупреждения основного пути нужно оценивать вместе с итогом альтернативного пути.

### 15.4. Контакт потолка

Для потолков строятся вертикальные объёмы контура помещения до высоты самого элемента. На пересечении рассматриваются поверхности, направленные вниз, с достаточно выраженной отрицательной вертикальной составляющей нормали. Это позволяет учитывать потолок выше верхней границы room solid и некоторые наклонные нижние поверхности.

Метод — `CeilingProbeIntersection`. Это не гарантия обработки любой криволинейной геометрии: булевы операции и доступность подходящих граней по-прежнему могут ограничивать результат.

### 15.5. Проецирование контура на высоту отделки

`FinishProjectedContactSource` дополняет перечисленные результаты:

1. Получает контур помещения через `GetBoundarySegments` на расчётной плоскости с границей `Finish`.
2. Поднимает/опускает его к диапазону конкретного элемента и создаёт вертикальные объёмы.
3. При невозможности получить такой контур использует нижние горизонтальные грани room solid.
4. Для стены проверяет реальные почти вертикальные плоские грани самой отделки с обеих сторон и измеряет пересечение тонкого выдавливания с объёмом помещения.
5. Для пола/потолка оценивает контакт нижних поверхностей пересечения.

Это помогает найти откос, расположенный выше room solid или внутри контура помещения, а также отделку при нескольких отметках пола. Метод — `ProjectedRoomFootprint`.

Если у перекрытия не удалось получить положительный контакт обычным пересечением, дополнительно триангулируются его реальные нижние поверхности. Треугольники рекурсивно делятся; центр каждой небольшой части проверяется через `Room.IsPointInRoom` на подходящей высоте внутри помещения. Это **приближённая контактная оценка только для выбора владельца**. Она никогда не становится опубликованной площадью ведомости.

В текущей реализации деление продолжается при площади треугольника больше 2,5 внутренних квадратных единиц и глубине меньше 7. Эта константа — техническая настройка fallback, а не пользовательский допуск площади.

### 15.6. Продолжение принадлежности по цепочке стен

`FinishConnectedWallContactSource` помогает с небольшими нераспознанными участками стеновой отделки:

- рассматривает стены с `LocationCurve`;
- требует совпадения типа и базового уровня;
- проверяет близость bounding box и соприкосновение кривых в плане с учётом толщины стен;
- строит компоненты ещё не назначенных стен;
- находит соседние стены с уже определёнными владельцами;
- назначает компоненту только при **единственном** владельце среди определённых соседей.

Если соседние подтверждённые стены относятся к разным помещениям, компонент остаётся неопределённым. Для такого контакта используется служебная оценка `1` и метод `ConnectedWallContour`; эта единица не является измеренной площадью детали. Итоговая площадь позже всё равно берётся из Revit.

### 15.7. Предотвращение повторного измерения

`FinishOccurrenceAccumulator` хранит результат по ключу `(RoomId, ElementId, Category)`.

- `Add` суммирует части, полученные одним методом.
- `KeepLargest` оставляет наибольшую оценку среди альтернативных способов той же пары.
- Альтернативные оценки не складываются как независимая отделка.

Некоторые предупреждения предыдущих путей убираются, если контакт той же пары успешно восстановлен методом `ProjectedRoomFootprint`. Но не все геометрические предупреждения автоматически исчезают после любого успешного fallback.

## 16. Единственный владелец и полная площадь

После получения контактов `FinishElementOwnershipResolver` группирует их **по физическому `ElementId`** и выбирает:

1. Наибольшую площадь контакта.
2. При равенстве — меньший `RoomId`.
3. Затем категорию как дополнительный детерминированный порядок.

Полная площадь читается из `BuiltInParameter.HOST_AREA_COMPUTED`, переводится из внутренних единиц Revit в квадратные метры и записывается в итоговый `FinishOccurrence` выбранного владельца.

Если полная площадь отсутствует, неположительна, `NaN` или бесконечна, элемент не получает опубликованное количество; создаётся `FullElementAreaUnavailable`. Площадь контакта не используется как замена.

Если элемент контактирует с несколькими помещениями, создаётся `MultipleRoomContacts` со списком кандидатов и контактных оценок. Это описание принятого выбора, а не автоматическое распределение.

Пример:

```text
Полная системная площадь потолка: 100 м².
Контакт с помещением 101: 60 м².
Контакт с помещением 102: 40 м².

Результат:
101 получает 100 м² этого элемента.
102 не получает части этого элемента.
Диагностика сообщает о нескольких контактах.
```

Если требуется ведомость именно по частям общей отделки, надо либо разделить физический элемент в модели, либо отдельно менять утверждённый контракт расчёта. Подмена этого правила в коде без согласования изменит смысл количеств, принадлежности, проверок и исторических сравнений.

«Полная площадь» означает системную площадь конкретного элемента, которую выдаёт Revit. Это не площадь всех граней solid, не площадь помещения, не `периметр × высота`, не отдельный подсчёт каждой материальной прослойки и не универсальное утверждение о геометрической площади всех поверхностей. Проёмы и особенности формы влияют на системную площадь так, как их учитывает Revit для данного элемента.

### 16.1. Почему сначала считаются все помещения

Если сначала ограничить геометрию выбранной секцией, общий элемент мог бы целиком перейти соседнему помещению только потому, что настоящий победитель находится вне секции. Текущий код сначала определяет владельцев по всему набору валидных помещений, затем оставляет результаты выбранной области.

При этом элементы с владельцами вне выбранной области исключаются из целей записи принадлежности. Найденные через продолжение стенового контура элементы с владельцами внутри области добавляются в цели, даже если не попали в первоначальный локальный список кандидатов.

Следствие: маленькая область отчёта не обязательно означает пропорционально маленькое время геометрического расчёта.

## 17. Нормализация описаний и группировка

### 17.1. Подготовка текста

`FinishDescriptionNormalizer`:

- обрезает внешние пробелы;
- превращает последовательности пробелов, табуляций и переносов строк в один пробел;
- для ключа сравнения использует `ToUpperInvariant()`;
- сохраняет человекочитаемый вариант для вывода;
- заменяет пустое описание маркером `[Описание не задано]`.

Таким образом, «Окраска  белая», « окраска белая » и «Окраска\nбелая» объединяются как одно описание. Различия в реальных словах, цифрах, знаках и пунктуации сами по себе не удаляются. Например, разные толщины в тексте могут создать разные группы.

### 17.2. Сначала внутри помещения

Для каждого помещения и каждой включённой категории собираются итоговые элементы владельца. Одинаковые нормализованные описания объединяются, а их полные числовые площади суммируются без промежуточного округления.

### 17.3. Потом между помещениями

`FinishGroupKeyBuilder` формирует ключ из категорий `W`, `F`, `C`, состояния каждой категории и отсортированных уникальных нормализованных описаний. Для защиты от неоднозначного склеивания используется префикс длины описания.

В ключ не входят:

- площади;
- номер, имя, ID помещения;
- этаж или секция как самостоятельные признаки;
- ID типа отделки;
- количество элементов одного описания.

Поэтому при расчёте всего объекта помещения разных этажей/секций могут объединиться, если их включённый состав и состояния совпадают. Ограничение областью нужно выбрать заранее, если такую общую группировку получать не требуется.

### 17.4. Пример группировки

Предположим, других различий включённых категорий нет:

| Помещение | Стены: описание | Стены, м² | Пол: описание | Пол, м² |
| --- | --- | ---: | --- | ---: |
| 101 | Окраска | 20 | Плитка | 10 |
| 102 | окраска | 30 | Плитка | 12 |

Оба помещения образуют одну группу. В каждое записывается:

```text
Список помещений: 101, 102
Описание стен: Окраска
Площадь стен: 50,00
Описание пола: Плитка
Площадь пола: 22,00
```

Эти `50,00` — сумма группы, а не индивидуальная площадь стен помещения 101 или 102. Если в сторонней спецификации включить отдельные экземпляры и просуммировать оба значения, получится ошибочное удвоение. Обычные текстовые выходы предназначены для отображения сгруппированного результата.

## 18. Состояния результата и форматирование

У каждой категории помещения есть состояние:

| Состояние | Значение | Отображение |
| --- | --- | --- |
| `Resolved` | Есть рассчитанные позиции без пометки неполноты этой категории | Описания и площади |
| `NoFinish` | В результате нет позиций и нет классифицированного как влияющее на значение предупреждения | `—` |
| `Unknown` | Есть предупреждение, влияющее на полноту этой категории | `[Не удалось определить]`, при необходимости вместе с рассчитанными позициями |

`NoFinish` и `Unknown` входят в ключ по-разному. Неизвестную отделку нельзя молча объединять с достоверным отсутствием отделки.

Если часть элементов определена, а часть вызывает неполноту, известные позиции сохраняются, и отдельно добавляется строка `[Не удалось определить]`. Маркер появляется синхронно в описаниях и площадях.

Важно: прочерк означает отсутствие позиций **по результату текущего поиска**, а не доказательство, что физической отделки в модели вообще нет. Например, элемент вне области поиска по высоте может остаться неучтённым без `Unknown` для конкретной комнаты.

`FinishAggregationFormatter`:

- сортирует описания и идентификаторы естественным порядком;
- выдаёт площади через `ToString("N2", ru-RU)`;
- использует десятичную запятую и возможный разделитель разрядов;
- не добавляет `м²` в значение параметра; единица есть в заголовке столбца;
- переносит длинные описания по словам, а слишком длинные слова — частями;
- учитывает настроенную ширину описания при оценке вместимости строки;
- размещает площадь около середины строк соответствующего описания;
- заполняет остальные строки столбца площади неразрывными пробелами `U+00A0`, сохраняя вертикальное соответствие.

Изменение ширины описания может изменить переносы и текстовые значения выходных параметров при неизменных физических суммах. Сравнение параметров нормализует переводы строк и внешние пробелы, но сохраняет значимые внутренние переносы/выравнивание.

Округление выполняется только здесь, после численного суммирования. Сумма видимых округлённых строк иногда отличается на сотые от округления общей исходной суммы; это нужно учитывать при проверках.

## 19. План записи и предварительные проверки

`FinishScheduleWriteWorkflow.Prepare()` заново выполняет расчёт и строит три части:

1. Обязательные значения выходных параметров помещений.
2. Необязательные значения принадлежности физических элементов.
3. План создания нового выпуска спецификации.

Формирование блокируется для:

- документа семейства;
- документа только для чтения;
- документа с уже открытой изменяющей транзакцией (`IsModifiable`);
- отсутствия валидных целевых помещений;
- невозможности построить агрегацию;
- критических проблем обязательных параметров;
- невозможности сохранить/мигрировать прежние управляемые выпуски;
- отсутствия или неподходящего типа обязательного шаблона оформления.

Перед записью каждого параметра проверяется существование элемента и параметра, `StorageType.String`, отсутствие `IsReadOnly` и отсутствие владения другим пользователем через `WorksharingUtils.GetCheckoutStatus`.

`FinishParameterChangePlanner` сохраняет предыдущее и новое значение. Уже совпадающие значения исключаются из плана записи. Сообщение подтверждения объясняет замены, очистку и изменения оформления текста; пользователь подтверждает конкретно подготовленную операцию.

Неполная геометрия сама по себе не всегда блокирует выпуск: плагин может сформировать ведомость с маркерами и предупреждениями. Нужно различать «критическое предупреждение полноты расчёта» и «критическую ошибку плана записи» — это разные уровни логики.

## 20. Что записывается и насколько операция атомарна

После подтверждения открывается общая `TransactionGroup`:

1. Прежние управляемые ведомости старого формата переводятся в выпуск с отдельными параметрами, пока обычные выходные значения ещё не изменены.
2. Выполняется необязательная запись принадлежности.
3. Записываются обязательные выходы помещений.
4. Создаётся и оформляется новый выпуск.
5. Все вложенные транзакции объединяются через `Assimilate`.

При ошибке обязательной записи, миграции или создания/оформления вида предусмотрен откат общей группы. Новые параметры выпуска и созданные виды не должны оставаться частично применёнными. Ошибки самого отката логируются отдельно; архитектурная гарантия не означает, что следует скрывать аварийный сбой Revit.

Во время записи повторно проверяются права и актуальность значений:

- если текущее значение уже равно новому — запись пропускается;
- если оно не равно ни старому, ни новому — для обязательного выхода помещения это ошибка и откат;
- для необязательной принадлежности такой элемент пропускается с предупреждением.

### 20.1. Принадлежность отделки

При выключенной опции плагин не трогает параметры принадлежности. Чтение старых значений принадлежности не определяет новый геометрический результат.

При включённой опции записываются идентификаторы из итогового расчёта. Хотя builder технически умеет соединять несколько идентификаторов, нынешний resolver выдаёт одного владельца на физический элемент, поэтому обычный результат — один идентификатор.

- При неопределённой геометрии, влияющей на принадлежность, запись элемента пропускается; прежнее значение сохраняется.
- Если элемент находится среди целей текущей области, но не имеет назначенного владельца и нет блокирующей неопределённости, принадлежность **очищается до пустой строки**, с предупреждением `UnassignedOwnership`.
- Элемент с владельцем вне выбранной области исключается из целей, поэтому его принадлежность не очищается только из-за ограниченного отчёта.
- Ошибка отдельного ownership-параметра не должна отменять корректную обязательную ведомость: элемент пропускается с предупреждением.

Обычные выходные параметры обновляются только у помещений текущей агрегации. Плагин не выполняет глобальную очистку всех ранее заполненных помещений проекта.

## 21. Как устроена спецификация

Создаётся `ViewSchedule` категории `OST_Rooms` через `ViewSchedule.CreateSchedule`. При трёх включённых категориях порядок **восьми видимых столбцов** такой:

| № | Столбец | Источник текущего расчёта | Ширина по умолчанию |
| --- | --- | --- | ---: |
| 1 | Наименование или номер помещения | Выходной список помещений группы | 40 мм |
| 2 | Стены или перегородки | Выходное описание стен | 80 мм |
| 3 | Площадь, м² | Выходная площадь стен | 25 мм |
| 4 | Потолок | Выходное описание потолков | 80 мм |
| 5 | Площадь, м² | Выходная площадь потолков | 25 мм |
| 6 | Пол | Выходное описание полов | 80 мм |
| 7 | Площадь, м² | Выходная площадь полов | 25 мм |
| 8 | Примечание | Системные «Комментарии» помещения, ID `-1010106` | 30 мм |

После фиксации выпуска вид показывает **собственные параметры выпуска**, содержащие копии этих значений. Изменение обычных выходов или комментариев после выпуска не обновляет соответствующие зафиксированные значения автоматически.

Для `k` включённых категорий число видимых столбцов равно `2 + 2k`. Отключённая категория убирает свою пару столбцов. При всех категориях ширина таблицы по умолчанию — `40 + 3 × (80 + 25) + 30 = 385 мм`.

Устанавливается `IsItemized = false`, сортировка/группировка по первому столбцу, без групповых заголовков, итогов и пустых строк между группами. Спецификация не вычисляет суммы отделки: она показывает уже подготовленные групповые тексты.

Первоначальный план содержит фильтр выбранного уровня/секции. В окончательно зафиксированном выпуске фильтры заменяются точным признаком принадлежности к выпуску. Поэтому более позднее изменение значения секции само по себе не должно просто расширить старый выпуск.

## 22. Сохранение отдельных выпусков

### 22.1. Имена

Свободное базовое имя используется без суффикса. Если оно занято, выбирается первый свободный вариант `(2)`, `(3)` и далее. Сопоставление существующих имён выполняется без учёта регистра.

Совпадение имени с чужой спецификацией не даёт права её перезаписать: выбирается новое имя. Управляемость определяется metadata TrueBIM.

### 22.2. Параметры отдельного выпуска

`FinishRoomVersionService` создаёт для каждого выпуска:

- по одному новому общему текстовому параметру экземпляра помещения на каждый видимый столбец;
- ещё один текстовый параметр «Состав выпуска» для включения нужных помещений.

При восьми столбцах это **девять новых определений параметров**. При `k` категориях — `3 + 2k`.

Пример схемы имени:

```text
TrueBIM • Отделка <ScheduleId> • <номер> <заголовок>
```

Для каждого выпуска генерируются новые GUID. Параметры видимы, но создаются с `UserModifiable = false`, то есть не предназначены для ручного изменения через интерфейс Revit. Это не криптографически неизменяемый архив: API и изменение структуры модели требуют отдельного контроля.

Параметры привязываются к категории помещений проекта. Значения заполняются у точного набора помещений выпуска. Скрытое поле членства фильтруется по тексту `"1"`.

Перед завершением сравниваются:

- точный набор ID помещений;
- отображаемые строки до и после преобразования, с нормализацией переносов.

Расхождение вызывает ошибку и откат.

### 22.3. Что сохраняется

- Выпущенные описания, площади, списки помещений и примечания.
- Состав помещений выпуска.
- Связь строк с исходными объектами помещений.
- Возможность стандартной команды Revit «Выделить в модели» для одной или нескольких комнат группы.
- Для мигрируемого прежнего вида — его ID, имя и существующее размещение на листах.

Это **снимок значений, связанный с живыми помещениями**, а не копия геометрии и не самостоятельная резервная RVT-модель. Удаление помещения или изменение его доступности для фазы/варианта вида может повлиять на обычные строки. Новые помещения с пустым параметром членства не добавляются в старый выпуск.

Удаление вида не удаляет автоматически его параметры выпуска. При множестве выпусков число параметров проекта растёт; отдельного сборщика неиспользуемых параметров в рассматриваемом пути нет.

### 22.4. Миграция предыдущих форматов

Metadata различает три поколения:

| SchemaVersion | Смысл |
| --- | --- |
| 1 | Ранняя управляемая спецификация на текущих обычных параметрах |
| 2 | Статический текстовый снимок с данными в заголовке |
| 3 | Текущий выпуск на отдельных параметрах настоящих помещений |

До новой записи плагин проверяет **все** старые управляемые спецификации помещений документа, нуждающиеся в миграции, а не только вид с текущим именем. Проблемная старая ведомость может поэтому заблокировать выпуск другой области.

Старые текстовые строки восстанавливаются по **уникальным существующим номерам помещений**, указанным в первом столбце. Неизвестный, повторяющийся или неоднозначный номер блокирует восстановление. Архив на основе имён помещений, изменённых номеров или неразрешимой строки нельзя надёжно мигрировать автоматически.

При миграции также ограничены вычисляемые поля, нетекстовые отображаемые параметры и сортировка по скрытым полям. Если прежняя ведомость занята другим пользователем или разделена на части, предварительная проверка блокирует её преобразование; для разделённого вида предлагается сначала объединить части. Сервис сохраняет штатную структуру поддержанного выпуска, а не произвольную пользовательскую таблицу любого вида.

Старый `FinishScheduleSnapshotService.Freeze()` остаётся в исходниках, но его нельзя снова подключать для новых выпусков: он относится к текстовому способу архивации. Текущий поток использует `FinishRoomVersionService`; часть функций SnapshotService нужна для сохранения/восстановления оформления заголовка и работы с наследием.

## 23. Оформление таблицы

Текущие константы `FinishRoomScheduleStyleRules`:

- revision оформления: `v23`;
- название в составной шапке: «Ведомость отделки помещений»;
- объединённый заголовок: «Вид отделки элементов интерьера»;
- название — 3,5 мм;
- заголовки и тело — 2,5 мм;
- три строки области шапки: название, групповой заголовок, названия столбцов;
- высоты этих строк: 12, 8 и 12 мм соответственно;
- вокруг названия границы отсутствуют;
- рамки табличной шапки и вертикальные линии — «Обычные линии»;
- промежуточные горизонтали — «Тонкие линии»;
- буквенная нумерация граф не добавляется;
- `ShowBlankLineBetweenGroups = false`.

Названия стилей линий сопоставляются с учётом возможных угловых скобок в Revit. Есть fallback на встроенные medium/thin line categories. Для границ используются ID категорий стилей линий, а не подстановка `GraphicsStyle.Id`.

Гарнитура и часть начертания наследуются из штатных типов текста спецификации. Для целевых размеров создаются/используются отдельные типы:

```text
TrueBIM • Ведомость отделки • Название 3,5 мм
TrueBIM • Ведомость отделки • Заголовок 2,5 мм
TrueBIM • Ведомость отделки • Тело 2,5 мм
```

Название принудительно получает жирное начертание; остальные параметры оформления зависят от исходных типов и правил конфигурации. Нельзя обещать конкретный шрифт вроде GOST Common в каждом проекте: он фигурировал в конкретной проверочной модели, а не как универсальное имя в настройках.

Собственные единицы `TableCellStyle.TextSize` и внутренние футы Revit различаются. Код содержит адаптацию единиц; при исправлении размера текста нельзя передавать одно и то же числовое значение во все API без конвертации.

## 24. Обязательный шаблон без пустой строки

Изменение 0.2.20 добавляет обязательный проектный шаблон спецификации помещений:

**`TrueBIM • Отделка • Без пустой строки`**

Его нужно подготовить один раз в проекте:

1. Открыть обычную спецификацию категории «Помещения».
2. В свойствах открыть настройку **«Вид → Изменить»**.
3. Снять **«Отделять данные пустой строкой»**.
4. Создать из вида шаблон с указанным именем.
5. Проверить, что в шаблоне галочка также снята.

Одно только имя не отключает пустую строку. Готовый RVT/RTE-шаблон не включён в этот программный путь; шаблон должен существовать в текущем проекте. Его можно хранить в проектном RTE или переносить средствами Revit.

Перед записью `FinishScheduleAppearanceTemplateService.Validate` проверяет наличие `ViewSchedule`-шаблона категории помещений и доступность раздела `SCHEDULE_SHEET_APPEARANCE_PARAM`. Само состояние галочки отдельным публичным свойством этот код не проверяет.

При применении:

- создаётся временная копия шаблона через `ElementTransformUtils.CopyElements`;
- у копии включается управление только разделом оформления, остальные разделы исключаются;
- вызывается `ApplyViewTemplateParameters` для однократного переноса;
- временная копия удаляется;
- исходный шаблон не редактируется;
- новый вид не остаётся постоянно привязанным к этому шаблону;
- поля, сортировку, фильтры и состав выпуска затем задаёт сам модуль.

Отсутствие шаблона блокирует формирование до записи обычных параметров. Ошибка применения участвует в общем откате. Старые выпуски автоматически не переформатируются этим новым правилом.

`ScheduleSortGroupField.ShowBlankLine` управляет пустыми строками между группами. Он не заменяет настройку отдельной строки между шапкой и данными.

## 25. Что происходит при ошибке составной шапки

Обычный режим — `FinishScheduleHeaderMode.Custom` с объединёнными ячейками. Если выбрасывается `FinishScheduleHeaderFormattingException`, весь текущий выпуск откатывается, и UI предлагает:

- повторить с простой шапкой Revit (`Standard`): название и стандартные заголовки без объединения;
- повторить без шапки (`None`): только данные;
- отменить.

Такой повтор использует подготовленный план, но вновь проверяет актуальность перед применением. Это специальное восстановление после ошибки составной шапки, а не универсальная возможность игнорировать любую ошибку или отсутствие шаблона.

## 26. Metadata управляемого вида

`FinishScheduleMetadataService` использует Revit Extensible Storage:

```text
Schema GUID: C72569A6-4C99-4CD0-92D0-0198730E4551
SchemaName: TrueBIMFinishSchedule
FeatureId: TrueBIM.FinishSchedule
CurrentSchemaVersion: 3
```

Сохраняются `SchemaVersion`, `FeatureId`, `SettingsHash`, `Scope`, `ParameterIdentities`, `LastUpdatedUtc`.

SHA-256 `SettingsHash` строится из revision оформления, имени, колонок, их identity/ширин/видов и фильтра области. Это fingerprint плана представления, а не хеш всей геометрии RVT, не полный аудит исходных значений и не механизм автоматического обнаружения любых изменений модели.

Признак управляемого вида требует правильного `FeatureId` и поддерживаемой версии metadata. Имя вида само по себе этого не доказывает. Названия `IsSnapshot` и `MarkAsSnapshot` сохранились исторически; для версии схемы 3 они относятся уже к снимку в параметрах помещений.

## 27. Локальный профиль и перенос конфигурации

### 27.1. Профиль пользователя

Путь: `%APPDATA%\TrueBIM\BimTools\finish-schedule\settings.json`.

`FinishScheduleProfileStorage` имеет ключ `finish-schedule`, текущую версию записываемого формата `2`, сохраняет все настройки запуска: выбранные параметры, категории, идентификатор, принадлежность, область, LevelId, значение секции, имя и ширины.

Это **локальный профиль текущего пользователя**, а не автоматически сохранённая в RVT конфигурация проекта. Название окна «Конфигурация проекта» обозначает назначение настроек, но не место их хранения. При открытии другого RVT выполняется попытка сопоставления параметров с его каталогом.

Профиль сохраняется кнопкой, перед формированием и при закрытии окна. Незавершённые настройки тоже можно сохранить. При отсутствии/ошибке чтения JSON возвращаются безопасные настройки по умолчанию с записью предупреждения. Некорректные значения enum и ширин нормализуются.

### 27.2. Экспорт/импорт проектной конфигурации

`FinishScheduleConfigurationStorage` использует отдельный JSON-формат **версии 1** и путь, выбранный пользователем.

В него входят:

- три значения классификации;
- источник состава;
- режим и параметр идентификатора помещения;
- параметр списка помещений;
- шесть выходных параметров описаний/площадей.

В этот файл **не входят** область текущего запуска, выбранный уровень, секция, имя выпуска, ширины, включённость категорий, флажок ownership и его параметры. Импорт сохраняет эти текущие настройки, обновляя перечисленные конфигурационные поля. Экспорт конфигурации не заменяет полный backup локального профиля.

JSON не переносит определения параметров Revit, шаблон оформления, геометрию, значения состава у типов или выпущенные ведомости. Он переносит настройки выбора. В другом проекте параметры и шаблон должны существовать или быть отдельно подготовлены.

## 28. Диагностика

Есть три уровня представления:

1. Короткая сводка в окне и статус результата.
2. Окно предупреждений с объяснениями и рекомендуемыми действиями.
3. Полный копируемый отчёт и журнал.

Журнал: `%APPDATA%\TrueBIM\Logs\truebim.log`.

В отчёт входят:

- найденные, обработанные, невалидные помещения и помещения вне области;
- количество собранных/классифицированных/попавших в область элементов;
- потенциальные пары пространственного поиска;
- количество итоговых связей и площади по категориям;
- количество групп и помещений с выходными значениями;
- план изменяемых, неизменных и заблокированных параметров;
- реально записанные значения и пропущенная принадлежность;
- имя и ID созданного вида;
- предупреждения с кодами и ID объектов;
- длительности этапов и показатели кэшей.

Счётчики «кандидаты в области», «контакты», «итоговые элементы владельца», «число записей параметров» и «число групп» обозначают разные сущности. Например, 340 записанных значений — это не 340 помещений и не 340 элементов отделки.

### 28.1. Коды геометрических предупреждений

| Код | Смысл | Влияет на `Unknown` по текущему классификатору |
| --- | --- | --- |
| `RoomNotFound` | Помещение исчезло/не найдено при геометрии | Да |
| `RoomGeometryUnavailable` | Не удалось получить геометрию помещения | Да |
| `ElementNotFound` | Физический элемент не найден | Сам по себе нет |
| `ElementGeometryUnavailable` | Не удалось получить solid элемента | Сам по себе нет |
| `WallFallbackUnresolved` | Есть пересечение стены, но контакт не определён надёжно | Да |
| `SlabGeometryUnsupported` | Основной метод не поддержал форму перекрытия | Да, если предупреждение не снято успешным восстановлением |
| `ProbeCreationFailed` | Не удалось построить проверочный объём | Да |
| `BooleanIntersectionFailed` | Ошибка геометрического пересечения Revit | Сам по себе нет |
| `ProjectedAreaUnavailable` | Пересечение найдено, подходящая контактная площадь не получена | Да |
| `FullElementAreaUnavailable` | Недоступна допустимая полная системная площадь | Да |
| `MultipleRoomContacts` | Выбран один из нескольких владельцев | Нет, но выбор требует осмысленной проверки |
| `UnassignedElement` | Классифицированный элемент не назначен, в том числе вне области поиска | Да, с 0.2.22 |

Это точное разделение текущего `FinishGeometryWarningClassifier`, а не утверждение, что все предупреждения из колонки «нет» неважны. Они могут указывать на реальные пропуски. Зелёный/успешный статус записи не является доказательством абсолютной полноты модели.

Отдельные предупреждения агрегации: `MissingDescription`, `MissingRoomIdentifier`, `UnknownQuantity`. Отдельные проблемы записи включают отсутствующий/закрытый параметр, чужое владение элементом, неверную конфигурацию, невозможность миграции и недоступный шаблон.

## 29. Известные ограничения, которые нельзя замалчивать

### 29.1. Шесть пропущенных полов в проверочной модели

В сравнении от 16.09.2026 найдены шесть полов, отсутствующих и в эталонной, и в новой ведомости. В базовой установленной DLL они отсекаются вертикальным диапазоном поиска пола **±304,8 мм** от основания помещения; это повторно подтверждено ручным аудитом 17.09.2026.

| ElementId | Помещения по контуру | Полная площадь, м² |
| --- | --- | ---: |
| 1957360 | 209 | 299,79 |
| 2700621 | 005 | 52,44 |
| 2707982 | 004 | 34,71 |
| 2708023 | 003 | 21,39 |
| 2725263 | 001, 002 | 40,45 |
| 2757257 | 006 | 67,23 |

Сумма опубликованных в отчёте площадей пропусков — **516,02 м²**. У пола помещения 209 верх примерно на 550 мм ниже основания помещения; у пяти подвальных полов — примерно на 1150 мм выше.

Проверка «новая ведомость совпадает с эталоном» не обнаружит общий пропуск двух ведомостей. Для полноты надо сопоставлять весь классифицированный набор модели с итоговыми учтёнными ID и отдельно проверять элементы вне пространственной области.

В 0.2.19–0.2.21 этот диапазон не исправлен. В 0.2.22 реализовано расширение по геометрии полов своего уровня и добавлены регрессионные тесты. Повторная проверка в модели после установки остаётся обязательной и пока не выполнена.

### 29.2. Общая отделка нескольких помещений

Полная площадь общего элемента назначается одному владельцу. Поэтому у соседнего помещения может быть прочерк, хотя геометрически часть потолка находится над ним. Это следствие действующего правила, а не обязательно потеря элемента.

Пример из отчёта: потолок `2466464`, около 401,00 м², перекрывает помещения 209 и 210, но учитывается целиком у 209. Другие общие элементы перечислены в отчёте сравнения.

### 29.3. Другие существенные ограничения

- Связанные модели не обходятся.
- Нет отдельного выбора фазы/варианта проекта.
- Дополнительные категории отделки сами по себе не распознаются.
- Сложная геометрия зависит от успеха Revit Boolean API и резервных контактных методов.
- Приближённый fallback может влиять на выбор владельца в пограничных случаях, хотя площадь остаётся системной.
- Параметры каталога проверяются по существующим образцам; отсутствие категории и частичная доступность требуют внимания.
- С 0.2.22 `UnassignedElement` строится по всему классифицированному набору; при расчёте всего проекта сохраняются и предупреждения для элементов вне областей поиска.
- В очень сложных моделях кэши и синхронный расчёт могут потребовать заметного времени и памяти; автоматическая отмена пользователем не предусмотрена.
- Дублирующиеся идентификаторы помещений могут сделать обозначение групп неоднозначным; миграция текстовых архивов по номерам специально строже.
- Старые выпуски зависят от существования настоящих помещений.
- Каждый выпуск добавляет параметры, которые не удаляются автоматически вместе с видом.
- Обычные выходные площади помещений — групповые текстовые данные, непригодные для прямого суммирования по всем экземплярам.
- Отсутствие шаблона блокирует выпуск, а неверно настроенная галочка в существующем шаблоне не определяется отдельной проверкой.
- Пользовательские изменения старой управляемой ведомости могут оказаться неподдерживаемыми для миграции.

## 31. Технологии и сборки

Основной код — **C#**, namespace `TrueBIM.App.Modules.FinishSchedule`, WPF-интерфейс, Revit API. Основной проект: `plugins/truebim/src/TrueBIM.App/TrueBIM.App.csproj`.

| Целевой Revit по конфигурации проекта | Framework |
| --- | --- |
| 2019–2024 | `net48` |
| 2025–2026 | `net8.0-windows` |

Сборки используют отдельные API DLL установленной версии Revit и условные константы `REVIT2020_OR_GREATER`, `REVIT2021_OR_GREATER`, `REVIT2022_OR_GREATER` и далее. В разных API отличаются, например, типы идентификаторов, единицы и способы определения текстовых параметров.

В подтверждённом пакете 0.2.19 собраны Revit **2021–2026**; API 2019/2020 на машине отсутствовали, поэтому их не включали. Наличие ветки `net48` для 2019–2024 в `.csproj` не означает, что каждая из этих версий включена в конкретный установщик или проверена в runtime.

Тесты чистой логики используют xUnit. Проверочный `TrueBIM.Revit.FinishScheduleHarness` отдельно собирает модели/сервисы/Revit-адаптеры для запуска сценариев внутри Revit. Dynamo в исторических прогонах использовался как средство запуска проверочного кода; пользователю штатного плагина Dynamo для кнопки «Ведомость отделки» не нужен.

**Тонкость `FinishOccurrence`:** та же модель используется сначала для контактной оценки, а после `FinishElementOwnershipResolver` — для полной площади. Поле `AreaSquareMeters` меняет смысл в зависимости от стадии. Разработчику нельзя случайно обойти resolver и отправить контактные значения в агрегацию.

## 35. Что в старом ТЗ уже не соответствует коду

| Раннее описание | Текущая реализация |
| --- | --- |
| Площадь элемента делится по комнатам через пересечение | Контакт выбирает одного владельца, публикуется полная `HOST_AREA_COMPUTED` |
| Потолки только из `OST_Floors`, `OST_Ceilings` не поддерживаются | Геометрический сборщик и классификация включают штатные потолки |
| Потолок ищется около верхней границы помещения / с пределом +2 м | Основной поиск учитывает основание помещения выше с перекрытием в плане |
| Параметры автоматически не создаются | Есть отдельная подтверждаемая команда стандартного комплекта |
| Можно использовать имя типа как текстовый источник | В изменениях 0.2.21 системное имя типа запрещено, предпочтителен состав |
| Повторно обновляется один управляемый вид | Каждый запуск создаёт отдельный именованный выпуск |
| Выпуск сохраняется текстовыми ячейками заголовка | Версия 3 сохраняется в параметрах настоящих помещений |
| Нет обязательного проектного шаблона оформления | Для новых выпусков нужен «TrueBIM • Отделка • Без пустой строки» |
| Можно опираться на фразу о выбранной фазе | Явной настройки фазы в актуальных settings/collector нет |

При конфликте источников сначала нужно проверить текущий вызываемый путь кода, затем актуальные отчёты изменений. Ранний ROADMAP полезен как история требований, но не как единственное описание фактического поведения.

## 36. Практическая диагностика типовых жалоб

| Жалоба | Что проверить |
| --- | --- |
| «Элемент есть, а площади нет» | Физическую категорию, типовую классификацию, bounds/уровень, диапазон пола, геометрию, владельца и `HOST_AREA_COMPUTED` |
| «Потолок не в том помещении» | Все контактные кандидаты, правило максимального контакта, наличие общего элемента, перекрывающиеся помещения/фазы |
| «Площадь больше площади комнаты» | Публикуется полная площадь элемента; общая отделка может целиком принадлежать одной комнате; строка может быть групповой |
| «Площадь выросла по сравнению со старой ведомостью» | Старое правило контакта против полной площади; сравнивать одинаковые наборы ID элементов |
| «Описание не похоже на эталон» | Точную identity источника: `• Состав`, `Состав`, прежнее `Имя типа`; значения конкретных типов |
| «Стало больше/меньше групп» | Состав, нормализацию, включённые категории, `Unknown`, область и смену источника |
| «Старый вид не обновляется» | Это ожидаемое сохранение выпуска; открыть новый вид |
| «Нулевые изменения, но появился новый вид» | Обычные параметры идемпотентны, выпуски создаются каждый раз |
| «Параметра нет в списке» | Тип/экземпляр, StorageType, категории, реальные образцы, read-only, неоднозначные определения |
| «Нельзя сформировать из-за старой ведомости» | Миграцию всех управляемых старых видов, уникальность номеров, текстовые поля, блокировки помещений |
| «Не выделяется помещение через строку» | Формат выпуска и SchemaVersion; текстовый архив 2 против room-backed 3 |
| «Перед данными пустая строка» | Настройку галочки в обязательном шаблоне и то, что проверяется новый выпуск |
| «Текст обрезается» | Ширину, шрифт, многострочность, переносы и фактическую выгрузку на лист из Revit |
| «Ownership пропал» | Попал ли элемент в цели без владельца; плагин может явно очищать такую принадлежность |
| «Записалось не всё» | Разделить обязательные выходы, мягкие пропуски ownership и отдельную операцию создания стандартных параметров |

Для воспроизводимой ошибки полезно передать: версию Revit, фактически загруженную версию DLL, название/область расчёта, выбранную identity источника, ID помещений/элементов, классификацию и состав типов, значения `HOST_AREA_COMPUTED`, код предупреждения, полный отчёт и ожидаемый результат с объяснением правила.

## 37. Правила продолжения разработки для другого ИИ

1. Сначала уточнить, какая часть должна измениться: поиск элементов, владелец, числовая площадь, текст состава, группировка, запись, версия или оформление. Исправление одного слоя не должно незаметно менять смысл других.
2. Не возвращать частичные контактные площади в опубликованные количества без явного изменения требований.
3. Не назначать полную площадь одного физического элемента нескольким помещениям.
4. Сохранять глобальное определение владельца до фильтра области, иначе запуск по секции начнёт менять принадлежность общих элементов.
5. Не лечить пропуски пола подгонкой чисел к старому эталону. Проверять конкретные ID и область поиска; общие пропуски эталона тоже являются пропусками.
6. Не заменять состав именем типа и не интерпретировать название параметра без его identity.
7. Не добавлять площади в ключ группировки, если пользователь хочет группировать по одинаковому составу.
8. Сохранять `NoFinish`, `Unknown` и пустое описание как разные ситуации.
9. Не округлять промежуточные суммы и не пересчитывать их из уже форматированных строк.
10. Не менять порядок описаний отдельно от соответствующих площадей.
11. Сохранять обязательную запись и выпуск атомарными; ошибки необязательного ownership обрабатывать отдельно.
12. Сохранять прежние выпуски до изменения обычных параметров помещений.
13. Не использовать старый `Freeze()` для новых строк данных: это снова уничтожит связь с помещениями.
14. Не перезаписывать виды только по совпавшему имени и не считать metadata-hash хешем всего расчёта.
15. При исправлении оформления проверять реальную спецификацию на листе, включая многострочные ячейки; компиляции недостаточно.
16. Отдельно сообщать результаты unit-тестов, сборки по версиям API, runtime в Revit, установки и проверки установленной DLL.
17. Перед редактированием проверить `git status` и diff; не откатывать чужую работу ради «чистого» состояния.
18. Не объявлять незапущенные сценарии проверенными. Существующие отчёты привязаны к своим версиям, модели и настройкам.
