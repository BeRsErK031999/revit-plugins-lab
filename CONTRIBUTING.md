# Как работать над плагинами вдвоём

## Ветка и pull request

1. Клонируй репозиторий под своим GitHub-аккаунтом и открой папку репозитория в ИИ-агенте. После принятия GitHub-приглашения можно отправлять свои ветки в этот репозиторий.
2. Запиши в GitHub Issue или общем чате, какой плагин берёшь, что должно измениться и в каких версиях Revit или AutoCAD это нужно проверить. Если оба работаете с одним модулем или общим файлом, согласуйте границы до правок.
3. Заведи ветку на одну задачу по одному плагину. На своём компьютере используй отдельный клон. Для параллельных задач на одном компьютере подойдут отдельные Git worktree. Перед переключением проверь `git status` и сохрани чужую незавершённую работу.

   ```powershell
   git clone https://github.com/BeRsErK031999/revit-plugins-lab.git
   cd revit-plugins-lab
   git fetch origin
   git switch -c codex/finish-schedule-room-filter origin/main
   ```

   Для следующей задачи начни с `git fetch origin` и новой ветки от `origin/main`. Продолжая ту же задачу, используй её ветку.

4. Проверь diff, добавь к коммиту файлы своей задачи и отправь ветку через `git push -u origin HEAD`. Репозиторий публичный. Модели заказчиков, рабочие DWG/RVT, учётные данные, локальные SDK, тестовые выгрузки и установщики оставляй вне Git.
5. Открой pull request в `main`. Укажи задачу, затронутый плагин и общие файлы, команды сборки и тестов с результатами, версию хоста и ручной сценарий. Отдельно перечисли проверки, для которых не было подходящей версии или модели. Второй разработчик смотрит diff и результаты перед слиянием. Если после синхронизации с `main` поменялся код, повтори затронутые проверки.

В TrueBIM держи логику в `plugins/truebim/src/TrueBIM.App/Modules/<Имя>` и используй существующие классы и шаблоны модуля. Подключай команду по примеру ближайшего аналога. Если нужен устанавливаемый модуль с `module.json`, проверь регистрацию и попадание манифеста в пакет. Сохраняй существующие ID модулей и совместимость сохранённых настроек. Правки общей ленты, реестра модулей, сборочных целей и установщика согласуй с коллегой и перечисли в PR.

## Что проверить перед слиянием

1. **Сборка и тесты.** Из корня для TrueBIM выполни команды ниже. Нужна версия .NET SDK из [global.json](global.json) и Revit API соответствующего года. Обычная сборка использует API 2022 и 2025. Для других затронутых выпусков используй [матрицу сборки](plugins/truebim/docs/packaging.md). Самостоятельные продукты проверяй по их инструкциям.

   ```powershell
   dotnet --list-sdks
   dotnet build TrueBIM.sln -c Release
   dotnet test TrueBIM.sln -c Release --no-build
   ```

2. **Запуск внутри Revit или AutoCAD.** Используй копию модели и отдельный профиль Windows или тестовую машину для установки. Перед локальным развёртыванием закрой хост. Запусти проверяемую версию хоста, открой плагин с ленты и воспроизведи основной сценарий и отмену или ошибочный ввод. Если команда меняет модель, проверь объём изменений и откат. Для TrueBIM используй [ручную проверку и локальное развёртывание](plugins/truebim/docs/manual-qa.md) или сценарий конкретного модуля.
3. **Соседние возможности.** Если менялась общая лента, загрузка, настройки или упаковка, запусти приложение и открой хотя бы один соседний модуль, который зависит от затронутой части. Для изменений установщика отдельно проверь состав пакета и установку на тестовом профиле. Разработчик проверяет свою сборку локально, общий установщик публикует владелец выпуска.

## Запрос для ИИ-агента

> Прочитай AGENTS.md, CONTRIBUTING.md и документацию нужного продукта. Задача — [что изменить], результат — [как проверить], целевой хост — [продукт и год]. Проверь статус Git, найди ближайший аналог и возьми отдельную ветку от origin/main. Продолжи существующую ветку, если задача уже начата. Сохрани чужие изменения. Если для задачи нужны правки общего кода, назови затронутые модули перед правками. Выполни доступные сборку, тесты и проверку на копии модели. Проверь diff и подготовь PR в main. В PR запиши, что реально запустилось, и какие проверки остались.
